# HITAPEX 遥测与游戏集成层分析报告

> 分析对象：HITAPEX（WPF / .NET 9.0 / x64，直驱方向盘遥测软件）的遥测与游戏集成层。
> 依据代码：`Services\` 下 6 个核心文件、`Assets\TelemetryConfigs\` 全部配置、`docs\` 下 API 文档与各游戏手册。行号引用均为当前工作区真实代码。

---

## 1. 模块定位与整体架构

HITAPEX 的遥测链路是"**游戏 → 原生/注入数据源 → TelemetrySDK.dll（C++ 适配层）→ TelemetryService（C# 轮询层）→ TelemetryPacketBuilder（打包层）→ USB 串口广播 → 方向盘设备**"。配置文件部署（`TelemetryConfigService`）、安装检测（`SteamInstallService`）、游戏启动（`GameLauncher`）构成上游支撑链。

```
┌────────────┐  UDP(20777/1024/30000/26666)   ┌─────────────────────────┐
│  游戏(31款) │ ─── 或共享内存(Local\*) ──────▶ │  TelemetrySDK.dll        │
│  原生遥测   │  ←── 或注入DLL插件(SCS/rF2/WRC) │  C++17 原生 x64, 5 个     │
└────────────┘                                │  cdecl 导出, 适配器工厂   │
                                              └───────────┬─────────────┘
                     TelemetryConfigService 部署配置/插件   │ P/Invoke
                     SteamInstallService 发现安装目录       │ (TelemetryAPI.cs)
                     GameLauncher 启动游戏(steam://run)     ▼
                                              ┌─────────────────────────────┐
                                              │ TelemetryService (60Hz 后台   │
                                              │ 线程 "TelemetryLoop")         │
                                              │ GetTelemetryData → 自适应maxRpm│
                                              │ → ProcessFrame               │
                                              └───────────┬─────────────────┘
                                                          │ OnPacketsBuilt(byte[][])
                                                          ▼
                                              ┌─────────────────────────────┐
                                              │ TelemetryPacketBuilder       │
                                              │ 每帧 5×64B 帧: 0x6101~0x6105 │
                                              └───────────┬─────────────────┘
                                                          │ App.UsbManager.SendToDevice
                                                          ▼
                                              ┌─────────────────────────────┐
                                              │ USB 串口/HID                │
                                              │ 基座 · 面盘 · 踏板 (各自直连) │
                                              └─────────────────────────────┘
```

- 单一数据源统一格式：SDK 内部 20 个 C++ 适配器（`docs\TelemetrySDK_API_Document.md` L1134-1164）把各游戏协议归一化为固定 512 字节 `NormalizedData`，C# 侧只面对一个结构体。
- **TelemetrySDK.dll 的存在形式**：项目根 `D:\HITAPEX\HITAPEX\TelemetrySDK.dll`（378,880 字节）。经 PE 头解析确认：`Machine=0x8664`（x64）、`OptionalHeaderMagic=0x20B`（PE32+），为原生 C++ 二进制（C++17/MSVC 2022，CRT 静态链接，见文档 L1170-1185），**无法反编译为 C#，只能通过 P/Invoke 调用**；二进制中可检索到 5 个导出函数名的 ASCII 字符串（StartTelemetry / GetTelemetryData / StopTelemetry / GetSDKVersion / GetSupportedFlags），与文档声明一致。csproj 中以 Content 方式随构建复制（`HITAPEX.csproj` L33-37）：`<Content Include="TelemetrySDK.dll"><CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory></Content>`，即 DLL 与 exe 同目录，由 .NET 按名称解析加载。

## 2. TelemetryAPI 分析（Services\TelemetryAPI.cs，共 310 行）

**2.1 P/Invoke 导入（静态 DllImport，非动态 LoadLibrary）**——`TelemetryAPI.cs` L14-33：

```csharp
[DllImport("TelemetrySDK.dll", CallingConvention = CallingConvention.Cdecl)]
[return: MarshalAs(UnmanagedType.U1)]
public static extern bool StartTelemetry(int gameId);        // L14-16

[DllImport("TelemetrySDK.dll", CallingConvention = CallingConvention.Cdecl)]
[return: MarshalAs(UnmanagedType.U1)]
public static extern bool GetTelemetryData(ref NormalizedData outData);  // L19-21

[DllImport("TelemetrySDK.dll", CallingConvention = CallingConvention.Cdecl)]
public static extern void StopTelemetry();                   // L24-25

[DllImport("TelemetrySDK.dll", CallingConvention = CallingConvention.Cdecl)]
public static extern int GetSDKVersion();                    // L28-29

[DllImport("TelemetrySDK.dll", CallingConvention = CallingConvention.Cdecl)]
public static extern ulong GetSupportedFlags();              // L32-33
```

要点：调用约定 `Cdecl`（与 DLL 的 `__cdecl` 匹配）；`bool` 显式 `UnmanagedType.U1` 保证 1 字节。

**2.2 NormalizedData 结构体（L44-126）**——`[StructLayout(LayoutKind.Sequential, Pack = 1)]`，与 C++ 端 `#pragma pack(push,1)` 对应（文档 L215）。布局：基础参数 `speed/rpm/maxRpm/gear/throttle/brake/steer`（L48-54）→ 5 个状态 bool（`MarshalAs(U1)`，L57-61）→ 3 组×4 轮胎滑移数组（`ByValArray SizeConst=4`，L64-66）→ ERS/发动机/TC-ABS/燃油/旗语（L69-89）→ **v2.0 第三批 17 字段**（clutch、圈速×5、胎温内中核×4、胎压、胎磨、刹车温度、排名、水温、油温、涡轮，L91-118）→ `validFlags`（**288B 偏移处**，L121）→ `_reserved[224]`（L124-125），固定 512 字节。这是 v2.0 破坏性迁移后的新布局（`docs\Update_Notes_v2.0.md` L12）。

**2.3 枚举与常量**：
- `GameId`（L133-187）：31 项，Steam 游戏用 Steam App ID（如 `AssettoCorsa = 244210`），非 Steam 用自定义 ID（`RBR = 22`、`LFS = 25`）。
- `ValidFlags`（L194-246）：bit 0-44 共 45 位字段掩码，第一批基础驾驶 bit0-14、第二批辅助 bit15-27、第三批竞赛深度 bit28-44。
- `FlagType`（L253-266）：None/Blue/Yellow/Black/White/Checkered/Penalty/Orange/Red/SC/VSC 共 11 种旗语。

**2.4 辅助方法**：`GetGearName`（L273-280，-1→"R"、0→"N"、1-10 数字）；`IsDataValid`（L283-284，`rpm>0 || speed>0` 判"在赛道上"）；`CreateNormalizedData`（L287-303，预初始化所有 4 元数组与 `_reserved`，避免 NRE）；`HasFlag`（L306-307，`(validFlags & flag) != 0`）。

**2.5 初始化与轮询流程**：`StartTelemetry(gameId)` 单次调用启动适配器（内部先停旧适配器再启新，文档 L102）；轮询为每帧 `GetTelemetryData(ref data)`；退出必须 `StopTelemetry()`（幂等）；`GetSupportedFlags()` 仅在启动成功后有效。SDK 文档强调"不要多线程同时调用 API"（L1022-1026），本工程由 TelemetryService 单线程满足此约束。

## 4. TelemetryPacketBuilder 分析（Services\TelemetryPacketBuilder.cs，共 385 行）

把 512 字节 `NormalizedData` 打包为 USB 协议帧。帧固定 **64 字节**（`FrameSize = 64`，L10），每帧包头 7 字节（`WriteHeader` L34-43）：

```csharp
frame[0] = 0x61;                                   // 帧头 ID
frame[1] = (byte)(packetType & 0xFF);              // 包类型 uint16 LE
frame[2] = (byte)((packetType >> 8) & 0xFF);
frame[3..7] = timestampMs uint32 LE;               // 模拟时间戳
```

五包类型（L13-20）：`0x6101` 车辆信息1（基础驾驶）、`0x6102`（刹车温度+胎内/中温）、`0x6103`（胎外温+胎核+胎压）、`0x6104`（胎磨+水温+油温+涡轮）、`0x6105` 比赛信息（圈数+排名+圈速）。

**字节布局与缩放**（以包1为例，L56-170）：
- **float32 LE 原样写入**（不做二次缩放——SDK 已归一化）：速度 offset 7-10（L63-64）、油门 17-20、刹车 21-24、离合 25-28、转向 29-32、ERS 电量 42-45、油量 52-55、油量百分比 56-59。
- **uint16 LE 截断缩放**：maxRpm、rpm 经 `Math.Clamp(x, 0f, 65535f)` 转 ushort（L67-80）。
- **单字节**：档位 offset 16（L86-89）；TC/ABS 级别 `(byte)Math.Clamp(...,0,255)`；旗语 clamp 0-10；ERS 回收 clamp 0-100。
- **bool→0/1**：5 个状态标志逐位写入 offset 33-37（L108-117）。
- **位操作**仅限 LE 低字节在前的手工拆分（如 L70-71 `frame[11]=(byte)(maxRpm&0xFF); frame[12]=(byte)((maxRpm>>8)&0xFF)`）。
- 每个字段都先 `HasFlag(data, ValidFlags.X)` 判 validFlags 再写入，无效字段保持 0（帧已清零）。

**档位映射**（`GearFromNormalized` L374-384）——协议约定 `0=N, 1-100=前进, 0xFF=倒挡`：

```csharp
return gear switch
{
    -1 => GearValue.Reverse,                  // 倒挡 → 0xFF
    0  => GearValue.Neutral,                  // 空挡 → 0x00
    >= 1 and <= 100 => (byte)gear,            // 前进挡直接映射
    > 100 => 100,                             // 截断
    _ => GearValue.Neutral
};
```

`BuildAllPackets`（L352-366）一次产出五包数组，时间戳默认 `Environment.TickCount`。数据流为"**值域已在 SDK 归一化 → 打包仅做类型收窄与 clamp**"，无曲线/分段缩放逻辑。

## 5. TelemetryService 核心循环（Services\TelemetryService.cs，共 450 行）

**线程模型**：单后台线程 `TelemetryLoop`（L179-184，`IsBackground=true`），`Start()`（L140-189）先 `StopInternal()` 停旧任务，再 `TelemetryAPI.StartTelemetry(gameId)`；失败触发 `OnStartFailed`。`StopInternal`（L201-226）取消 CTS、`Join(500ms)`、调 `StopTelemetry()`、触发 `OnStopped`。状态（`_isRunning/_currentGameId`）全部 `lock(_lock)` 保护（L108-129）。

**轮询频率**：`LoopInterval = 16ms`（L27），用 Stopwatch 实测帧耗时后 `WaitOne` 补偿睡眠，超时 10ms 打警告（L264-275）——目标 **~60Hz**，与 SDK 文档建议一致（文档 L133）。

**主循环**（L240-276）：

```csharp
while (!token.IsCancellationRequested)
{
    var tickStart = Stopwatch.GetTimestamp();
    frameCount++;
    if (TelemetryAPI.GetTelemetryData(ref data))      // 有数据才处理
    {
        ApplyAdaptiveMaxRpm(ref data);                // 自适应 maxRpm
        ProcessFrame(data);
    }
    if (frameCount % ProcessCheckIntervalFrames == 0) // 每300帧≈5s
    {
        if (!IsTargetProcessAlive())                  // 游戏进程退出检测
        {
            Task.Run(() => Stop());                   // 自动停止
            break;
        }
    }
    ...
}
```

**进程保活检测**：`GameProcessNames` 静态表（L38-81）把 GameId 映射到 1~3 个进程名（如 EA WRC 含 `EAAntiCheat.GameService` 防作弊进程 L70；RBR 含 `RSF_Launcher` L79），每 5 秒 `Process.GetProcessesByName` 探测，游戏退出自动停遥测；未知进程名保守返回 true（L298-303）。

**自适应最大转速**（L33-35, L352-378）：LFS(25)/RBR(22)/BeamNG(284160) 三款协议无 maxRpm，启动时用默认 6000 RPM，随后追踪 rpm 峰值，连续 300 帧（5 秒）转速为 0 视为换车并重置。

**打包与下发**：`ProcessFrame`（L325-344）用 `Stopwatch.GetElapsedTime(_telemetryStartTick)` 生成模拟时间戳 → `BuildAllPackets` → 触发 `OnPacketsBuilt` → `DispatchPackets`。`DispatchPackets`（L388-433）经 `App.UsbManager` 广播：仅向"正常模式"设备（`DeviceRegistry.IsNormalMode`，跳过固件更新模式）逐设备逐包 `SendToDevice`，某设备一包失败则跳过该设备其余包；最后从包0的 timestamp 回读并触发 `OnPacketsDispatched(timestampMs)`。

**事件发布（全部在后台线程触发，UI 需自行 marshal）**：`OnStarted(gameId)`、`OnStartFailed(gameId)`、`OnStopped()`、`OnPacketsBuilt(byte[][])`、`OnPacketsDispatched(uint)`（L88-101）。UI 侧 `GameUserControl.StartTelemetrySimulation`（`Views\GameUserControl.xaml.cs` L1297-1341）订阅后用 `Dispatcher.BeginInvoke` 切回 UI 线程刷新发包计数。服务在 `App.InitializeUsbManager` 中创建（`App.xaml.cs` L166），`OnExit` 中 Dispose（L112）。

## 6. 游戏启动与检测

**GameLauncher（Services\GameLauncher.cs，135 行）**：双模式启动（`LaunchMode` L11-17）。CustomPath 用 `Process.Start` 直启 exe（L51-56）；Steam 模式校验 SteamId 纯数字（防注入，L71）后 `steam://run/{SteamId}`（L79-85）：

```csharp
Process.Start(new ProcessStartInfo
{
    FileName = $"steam://run/{game.SteamId}",
    UseShellExecute = true
});
```

启动后 fire-and-forget `StartTelemetryAsync`（L100-134）：解析 SteamId → `Enum.IsDefined(typeof(TelemetryAPI.GameId))` 白名单校验 → **延迟 5 秒**（给游戏加载时间）→ `telemetryService.Start(steamAppId)`。启动入口在 `Views\GameUserControl.xaml.cs` L643/956/1142 与 `Views\HomeUserControl.xaml.cs` L1204，由 `LaunchMode` 决定模式。

**SteamInstallService（Services\SteamInstallService.cs，211 行）**：纯静态无状态。路径发现链：`GetSteamPath`（L106-118）读注册表 `HKCU\Software\Valve\Steam\SteamPath` → 主目录 + `ParseLibraryFoldersVdf`（L124-154，解析 `"path"\t\t"D:\..."` 行、还原双反斜杠）收集所有库 → `FindGameManifest`（L57-76）在 `{library}\steamapps\appmanifest_{id}.acf` 中匹配 → 解析 `"installdir"` 拼出 `{library}\steamapps\common\{installdir}`（L64-71），并解析 `LastPlayed` Unix 时间戳（L187-210）供 UI 显示"上次游玩"。`CheckInstalled`（L36-49）批量查询返回 `SteamId → SteamInstallInfo`。

**配置部署时机**：`GameUserControl` 的"配置"按钮（L406-421）手动触发 `TelemetryConfigService.ApplyConfig(_selectedGame)`，成功/失败弹不同 Toast；`GameItem.NeedsTelemetryConfig`（`Models\GameItem.cs` L51）控制按钮是否显示（`Models\GameListConfig.cs` 硬编码 31 款游戏元数据，与 `TelemetryAPI.GameId` 一一对应）。注意：**配置部署与启动是解耦的两个手动步骤**，启动本身不自动部署配置。

## 8. 归一化参数（docs\manual\归一化参数.md）

关键定义：
- **基础**：`speed` km/h；`rpm`；`gear`（0=N，1-8 前进，-1=R）；`throttle/brake` 0-1；`steer` -1(左)~+1(右)。
- **状态标志**：`isPitLimiterActive/isTcActive/isAbsActive/isDrsAvailable/isDrsActive` 布尔。
- **轮胎数组**固定 `[0]=FL, [1]=FR, [2]=RL, [3]=RR`（4 轮顺序约定贯穿全部胎参）。
- **滑移**：`slipRatio` 纵向（-1~+inf）、`slipAngle` 弧度、`combinedSlip` 正交合成。
- **ERS/发动机/TC-ABS 档位**：不支持时填充默认值（文档仍写 `-1.0` 哨兵，但 v2.0 已改为置 0 + validFlags 判定——该手册为 v1 遗留，见第 9 节）。
- **燃油**：`fuelRemaining` 升（AC/ACC/F125 原始 kg，按汽油密度 ~0.75 kg/L 转换）、`fuelRemainingPct` 0-1。
- **旗语** `FlagType` 11 值枚举。
- **v2.0 变更**：`tyreWear` 由 0-1 改为 **0-100 递增百分比**；第三批 17 字段（离合、圈速×5、胎温内/中/外/核×4、胎压、胎磨、刹车温度、排名、水温、油温、涡轮）；SDK 内部 `SanitizeNormalizedData` 对超界/NaN/Inf 一律置 0，**判有效性必须用 validFlags**（文档 L423-424；Update_Notes L195-206）。
- 覆盖总览表（L108-139）逐游戏标注 OK/间接/近似/默认/-，例如 LFS/BeamNG 缺 `steer`（OutGauge 协议无转向），DiRT 系列燃油字段实际无效。

## 9. 代码质量与潜在问题

**架构优点**：① 单一归一化模型 + 掩码机制，扩展游戏只改 SDK 不动打包层；② 60Hz 循环用 Stopwatch 自校准，进程退出自动停采集；③ 五包广播对设备逐包容错（失败即停该设备）；④ 配置文件部署对 LMU 做了"保留已有值"的合并式 JSON 写入，EA WRC 注入避免整体重序列化以保格式。

**潜在问题**：
1. **缺失 DLL 无优雅降级**：`TelemetryService.SdkVersion`（L120）和 `Start()` 首次 P/Invoke 若找不到 TelemetrySDK.dll 会抛 `DllNotFoundException`/`BadImageFormatException`，启动流程（L156）未做 try/catch 与提示。
2. **配置覆写破坏用户设置**：LFS `cfg.txt`、DiRT `hardware_settings_config.xml` 是**整文件覆写**（含分辨率 2560×1369、刷新率 99Hz、音频等无关项），会重置用户自定义（手册建议改后设只读；代码未设只读）。WRC DLL 替换对游戏更新无感知，需用户重跑配置。
3. **文本级 JSON 注入脆弱**：EA WRC `InjectEaWrcPackets` 靠"缩进/括号深度/字符串匹配"定位 `packets` 数组（L544-622），换行风格或 `"packets": [` 前后有空格即可能失配；缩进计算 `indent/4+3` 是启发式。
4. **文档与代码漂移**：`GetSDKVersion` 文档写"当前返回 1"（文档 L178）但版本为 v2.0.0；`归一化参数.md` 仍描述 `-1` 哨兵语义，与 v2.0 置 0 行为冲突（Update_Notes L15）；文档示例 `GetGearName` 只映射 1-8 挡而代码支持 1-10。
5. **事件线程语义**：5 个事件全部在后台线程触发，服务层不做 Dispatcher 封送，若未来订阅者直接操作 UI 控件会抛线程异常（当前 UI 订阅均已 `Dispatcher.BeginInvoke`，靠约定维持）。
6. **竞争细节**：`ApplyAdaptiveMaxRpm` 的状态字段（`_trackedMaxRpm/_rpmZeroFrameCount`）在 `Start()`（L171-175）与循环线程间无锁，依赖"先 Join 旧线程再初始化"的顺序；`Task.Run(() => Stop())`（L259）与调用方 `Stop()` 并发时 `_loopThread.Join(500)` 可能因线程尚未退出而仅打警告，极端情况下旧线程残留。
7. **EA WRC 地址 `127.0.1.1`（L379）**与注入条目的 `127.0.0.1`（L630 等）不一致，疑似笔误，若游戏严格按配置连 `127.0.0.1` 会导致 WRCG 遥测连不上（需实测确认游戏对该字段的解析方式）。
8. **无卸载/还原流程**：除 WRC 有备份还原外，SCS 插件、LMU JSON、DiRT/F1 配置均无"移除配置"操作；`ApplyLmuPluginJson` 重序列化整个 JSON 可能丢失注释与未知字段格式。
9. **调试输出依赖 `Debug.WriteLine`**：Release 构建下所有遥测诊断静默，`OnPacketsBuilt` 等事件仅用于调试，缺少产品级日志（与 `Services\Usb\DeviceLogger.cs` 的日志体系未打通）。
10. **游戏列表双源维护**：`Models\GameListConfig.cs` 硬编码 31 款与 SDK 的 `GameId` 枚举、`GameProcessNames` 表、`TelemetryConfigService` 分发表四处重复维护游戏 ID，新增游戏需同步修改四处，易漏（如未来新增游戏若漏 `GameProcessNames` 条目，进程检测会保守跳过）。

**结论**：集成层整体设计清晰——SDK 负责"协议归一化"，C# 侧专注"轮询→打包→广播"，配置部署按游戏分派；主要风险集中在配置文件覆写破坏性、文本注入脆弱性、文档漂移与 DLL 缺失时的崩溃路径。
